Jak przebiega event FM 2026? — agenda, zasady, kontakty awaryjne ▼

Stan D — komentarz (v5 — queue model)

  • Spotkania FM = system kolejkowy, nie kalendarz. Uczestnik dostaje numerki, śledzi wywołania w aplikacji + na ekranie sali, idzie do Gate 1/Gate 2 gdzie obsługa FM odprowadza go na spotkanie. To NIE jest harmonogram z godzinami i stolikami.
  • Meeting row pokazuje wyłącznie: numer spotkania + nazwa sieci + status (sieć główna / rezerwowa). Brak godzin, brak stolików, brak kontaktów kupca — bo tych danych nie ma w schemacie FM.
  • Komunikat operacyjny w FM Hero: tłumaczy mechanikę (ekran + aplikacja → numer → Gate → obsługa FM odprowadza). To zastępuje fałszywą iluzję „kalendarza".
  • Logistyka eventu: Data + Rejestracja od 09:00 + Otwarcie 10:00 + Miejsce + sekcja „Obsługa spotkań B2B" z chip'ami Gate 1 / Gate 2.
  • Next Step: „Przygotuj materiały na spotkania z 4 sieciami" — sieci po nazwach, nie konkretne kupce. Goto: „Profile sieci".
  • Jeden gradient = FM Hero (zielony). Next Step to biała karta z lewym amber paskiem.
  • Sidebar identyczny porządek, FM ma badge „4" (liczba spotkań). Pod-nav: ✓ Wybór sieci · ✓ Algorytm · Twoje spotkania (active).

⚠ Model biznesowy spotkań FM 2026 — zasada fundamentalna

FM B2B działa jako system kolejkowy / wywoławczy, NIE jako klasyczny harmonogram. Implementacja Stanu D w P1 MUSI respektować ten model:

Co JEST w danych grafiku FM:

  • numer spotkania (kolejność w grafiku)
  • sieć handlowa
  • status sieci (główna / rezerwowa) — pochodzi z fm_prefs

Czego NIE MA w danych — UI nie wymyśla:

  • godzin spotkań (np. 10:30 — 10:50)
  • numerów stolików (np. B-14, sektor niebieski)
  • nazwisk kupców (np. Anna Nowak)
  • kontaktów do kupców (mail, telefon)
  • wiadomości od konkretnego kupca
  • komunikatów typu „bądź 15 min przed pierwszym spotkaniem"

Mechanika w dniu eventu:

  1. Uczestnik ma w aplikacji listę swoich spotkań (numer + sieć).
  2. Aktualne wywołania pojawiają się na dużym ekranie w środku sali ORAZ w aplikacji.
  3. Gdy numer uczestnika jest wywoływany → podchodzi do Gate 1 lub Gate 2.
  4. Obsługa B2B Fresh Market odprowadza go na właściwe spotkanie z siecią.
  5. Po zakończeniu wraca do trybu śledzenia kolejki.

Komunikacja przez ekran, aplikację, mikrofon i czasem SMS (źródło: kompendium FM PRECONNECT_KOMPENDIUM_DLA_GPT.md).

  • Sidebar stabilny — PreConnect zawsze pierwszy, FM zawsze drugi. Sygnał FM-aktywne = pulse-dot (Stan C) lub badge (Stan D).

Logika wyboru stanu (do implementacji)

function pickDashboardState({ co, fmSettings }) {
  // 1. Konto czeka na akceptację → blokery
  if (co?.account_status === "pending_review") return "B";

  // 2. Grafik FM opublikowany → operacyjny widok eventu
  if (fmSettings?.planPublished) return "D";

  // 3. Faza wyboru sieci otwarta, ale plan jeszcze nie wydany
  if (fmSettings?.schedulingOpen && !fmSettings?.planPublished) return "C";

  // 4. Domyślnie: codzienny PreConnect
  return "A";
}
  • Sprawdzaj w tej kolejności — pierwszy match wygrywa. Pending zawsze ważniejszy niż faza FM.
  • planPublished i schedulingOpen już są w fm_settings (sprawdzone w kodzie istniejącego PageSupplierDashboard). Nie wymagają nowych pól w bazie.
  • Stan A → Stan D ma sens jako naturalny upgrade pod koniec września. Po evencie wracamy do Stanu A (PreConnect całoroczny).
  • Stan B → Stan A automatycznie po zmianie account_status na active przez admina.

Wdrożenie — sugerowana sekwencja

  • Etap 1 (P0, 1–2 dni): Stan A + Stan B w PreconnectFM.jsx. Wymaga: helper getSupplierStats(accountId, 30d) + komponenty <NextStep/> <PkgCard/> <NextWindow/> <KpiRow/> <Activity/>. Bez zmiany sidebar.
  • Etap 2 (P0+, 1 dzień): getSupplierActivity — agregator zdarzeń z legacy_sends + legacy_offers + payu_orders + refundNotifs.
  • Etap 3 (P1, na wrzesień): Stan C + D — <FmHeroPickStep/> (preferencje) i <FmHeroPublished/> (plan + lista spotkań). Triggerowane przez fmSettings.currentPhase + schedulingOpen.
  • Stan D zależy od istnienia tabeli z grafikiem — sprawdź czy fmSchedule już zwraca pełne dane z numerami stolików i godzinami.
